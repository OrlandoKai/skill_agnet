# 实验记录

生成日期：2026-07-25

## 1. 实验目标

本实验用于比较三版 Agent 在 SkillBench-Mini 上的表现：

```text
task -> skill retrieval -> skill calling -> observation -> final answer -> evaluation
```

当前 benchmark 设置：

- Skill 数量：40 个 callable skills
- Task 数量：120 条
- 任务分布：60 条 single_skill，40 条 multi_skill，20 条 no_tool
- Retriever：Full Prompt、BM25、Embedding
- 本地模型：GGUF 本地模型，通过 llama-cpp-python 调用，不使用远程 API

主要评估指标：

- Skill Recall@k
- Skill Selection Accuracy
- Need Tool Accuracy
- No-tool Accuracy
- Unnecessary Tool Call Rate
- Skill Sequence Accuracy
- Under-call Rate
- Strict Task Success Rate
- Invalid Tool Call Rate
- Average Steps

## 2. 三版 Agent 操作流程

### 2.1 Baseline Agent

对应实现：`MinimalSkillAgent`

流程：

```text
task
-> retriever 检索 candidate skills
-> Llama 从 candidate skills 中选择一个 skill 或 NONE
-> call_skill(skill, input)
-> 得到 observation
-> 最多重复 max_steps 次
-> Llama 根据 task 和 observations 生成 final answer
-> evaluation
```

特点：

- 没有 NEED_TOOL / NO_TOOL 前置判断。
- 没有显式 planner。
- 每一步都让模型临时决定调用哪个 skill。
- 容易出现 no-tool 误调用、多技能漏调、相似 skill 选错等问题。

### 2.2 Enhanced Agent

对应实现：`EnhancedSkillAgent`

流程：

```text
task
-> NEED_TOOL / NO_TOOL 判断
-> 如果 NO_TOOL：直接回答，不调用 skill
-> 如果 NEED_TOOL：retriever 检索 candidate skills
-> Llama 生成 planned_steps
-> 依次 call_skill
-> 得到 observations
-> observation-grounded final answer
-> evaluation
```

特点：

- 增加了工具使用前置判断。
- no-tool 任务不再直接进入 skill retrieval / calling。
- 增加了 planned_steps，开始显式建模 skill sequence。
- 仍然依赖一次性 retrieval 和 Llama planner，因此 multi-skill 第二步可能漏检索或选错。

### 2.3 Enhanced V2 Agent

对应实现：`EnhancedSkillAgentV2`

流程：

```text
task
-> NEED_TOOL / NO_TOOL 判断
-> 如果 NO_TOOL：直接回答
-> 如果 NEED_TOOL：
   -> task decomposition，拆成最多 2 个 subtask
   -> 对整条 task 和每个 subtask 分别 retrieval
   -> rule backfill 补入明显相关 skill
   -> 每个 subtask 选择对应 skill
   -> skill-specific input builder 构造工具输入
   -> call_skill
   -> observation
-> rule-based / observation-grounded final answer
-> evaluation
```

特点：

- 引入 step-aware retrieval，缓解 multi-skill 第二步 skill 漏召回。
- 引入 deterministic backfill，按触发词补入关键 skill。
- 引入 skill-specific input builder，例如 percentage、unit conversion、translation direction、CSV、regex、`$PREVIOUS_OUTPUT`。
- final answer 主要基于 observation 规则生成，减少 final answer hallucination。
- 当前版本更像一个可解释的 rule-assisted Agent，而不是纯 LLM planner。

## 3. Baseline 结果

结果文件：

- `results/run_full_120.jsonl`

- `results/run_embedding_120.jsonl`

| Method | Recall@k | Selection Acc | Need Tool Acc | No-tool Acc | Sequence Acc | Under-call | Strict Success | Invalid | Avg Steps |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Full | 100.00% | 11.67% | 84.17% | 0.00% | 11.67% | 95.00% | 10.00% | 0.83% | 1.21 |
| BM25 | 91.50% | 45.00% | 82.50% | 0.00% | 44.17% | 82.50% | 40.00% | 0.83% | 1.08 |

主要现象：

- Full Prompt 的 Recall 最高，但 Selection Acc 很低，说明候选过多会干扰模型选 skill。
- BM25 和 Embedding 缩小候选空间后，selection 和 strict success 明显优于 Full。
- 所有 baseline 的 No-tool Acc 都是 0%，说明原始 Agent 几乎总是倾向调用工具。
- multi-skill under-call 严重，模型经常只调用一个 skill。

结果文件：

| Method | Recall@k | Selection Acc | Need Tool Acc | No-tool Acc | Sequence Acc | Under-call | Strict Success | Invalid | Avg Steps |

| Enhanced Embedding | 93.50% | 76.67% | 100.00% | 100.00% | 75.00% | 50.00% | 68.33% | 3.33% | 1.13 |

主要现象：

- NEED_TOOL / NO_TOOL 前置判断非常有效，No-tool Acc 从 0% 提升到 100%。
- Unnecessary Tool Call Rate 从 baseline 的接近 100% 降到 0%。
- Skill Selection Accuracy 明显提升。
- 剩余问题主要转移到 retrieval 覆盖、多技能漏调、planner 非法输出、相似 skill 选择和输入构造。

典型失败：

- `task_016`：需要 calculator + summarizer，但 summarizer 没进入 BM25 top-k，第二步选错。
- `task_017`：翻译方向可能选错。
- `task_023`：planner 可能生成不存在的 skill。
- `task_045`：percentage_calculator 选对了，但 input 构造错误。

主要现象：

- Step-aware retrieval 和 rule backfill 解决了多技能第二步 skill 漏召回问题。
- Skill-specific input builder 解决了大量 input construction 错误。
- Observation-grounded final answer 避免了工具输出正确但最终答案编造失败的问题。
- Enhanced V2 BM25 和 Enhanced V2 Embedding 在当前 120-task benchmark 上达到 100% strict success。

Enhanced V2 Full 的唯一失败：

- `task_080`
- instruction: `Find x when 5*x - 10 = 15.`
- gold skill: `equation_solver`
- called skill: `calculator`
- 原因：Full Prompt 给出了全部 40 个 skill，模型在 equation_solver 和 calculator 之间选择了更泛化的 calculator，导致输入 `5*` 执行失败。

## 7. 实验结论

1. 原始 Baseline 证明了最小闭环可以跑通，但不具备稳定的工具使用决策能力。
2. Enhanced Agent 证明 NEED_TOOL / NO_TOOL 前置判断是有效的，尤其能解决 no-tool 误调用问题。
3. Enhanced V2 进一步证明：多步任务不能只做一次 retrieval，需要按 subtask 做 step-aware retrieval。
4. Full Prompt 不是越多越好。即使 Recall 满分，候选过多也会增加相似 skill 选择错误。
5. BM25 和 Embedding 在 Enhanced V2 下都表现很好，说明规则化 pipeline 分解后，retriever 差异在当前 benchmark 上被显著缩小。
6. 当前 Enhanced V2 在 120-task benchmark 上接近满分，需要警惕 benchmark overfitting。

## 8. 下一步计划

1. 构造 held-out benchmark，加入模板外表达，验证 Enhanced V2 是否真正泛化。
2. 减少规则 backfill 对 benchmark 关键词的依赖，测试更弱规则或无规则条件下的性能。
3. 加入 ablation study，例如：
   - no gate
   - no step-aware retrieval
   - no rule backfill
   - no input builder
   - no observation-grounded final answer
4. 继续整理 MetaTool、ToolBench、StableToolBench、API-Bank、BFCL 中关于 no-tool decision、tool sequence correctness 和 function calling evaluation 的设定。
5. 在报告中明确区分：
   - retrieval improvement
   - selection improvement
   - planning improvement
   - input construction improvement
   - final-answer grounding improvement
